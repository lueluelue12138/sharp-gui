## Context

已合入主线的三个工作台位于 `a316b28d`，清单声明 runtime 7。当前更新器的 `compare_manifest_compatibility()` 在检查阶段和 helper 检出前均要求包元数据中的 runtime 与目标完全相同，且不会安装应用依赖。

调研得到的实际边界如下。

| 基线 | 已知变化 | 迁移判断 |
| --- | --- | --- |
| v2.0.0 / runtime 4 | 已发布带受管 Git、MinGit 的原始 ZIP | 首轮必须验证的旧包 |
| runtime 5、6 | 压缩与内容裁剪变化，未新增应用必需依赖或升级 Python/Torch/CUDA | 不能仅凭版本号差异判为基础环境不兼容，4、6 需实包验证，5 若有实际分发也纳入 |
| 当前 main / runtime 7 | 工作台加入 `websocket-client>=1.8,<2` | 需要受控补齐应用依赖，不能让用户丢失实时进度来迁就更新 |

一个清单中的单个数字无法同时满足旧 runtime 4 和 6 更新器的相等检查。单独发布“同版本号的过渡标签”还会被后来的最高 Stable 标签或 main 取代，无法覆盖暂时离线的旧用户。

原更新器已有可信 Git exact SHA、外部 helper、安装级锁、重启验证和失败恢复。沿用这些能力，扩展兼容性与依赖事务，避免再建立另一套常规更新系统。

## Goals / Non-Goals

**Goals:**

- 验证并打通已发布受管便携包到新工作台版本的升级，无需重新构建完整包。
- 后续同一基础环境上的应用依赖新增、升级、移除和 Stable 降级均有确定的更新路径。
- 用户批准一次更新后，自动准备依赖和应用，失败保留或恢复之前可用的组合。
- 在发布检查中明确验证跨版本更新，避免再出现“新版更新器写好了但旧版到不了”的缺口。

**Non-Goals:**

- 自动更换基础 Python、CUDA、PyTorch、原生工具或显卡驱动。
- 自动管理外部 ComfyUI、节点、模型或任意第三方软件。
- 未验证即宣布所有历史便携包兼容，或把无 Git 快照自动初始化为受管安装。
- 自动安装任意 requirements、源码分发包或未知原生扩展，提供用户自选包管理界面。

## Decisions

### 1. 基础兼容性、包布局和应用依赖分别表达

目标清单增加显式基础环境兼容声明和应用依赖锁摘要。保留现有字段以识别历史清单，`portable-package.json` 继续保留出厂环境与来源，不改写它伪装升级成功。

兼容声明按便携 target 列出经过验证的出厂基线，并检查所需 Python 版本、架构和关键运行能力。未列入的基线、不能满足的基础环境或缺失的关键工具仍安全拒绝。缺少新声明的历史目标维持旧清单处理规则。包压缩和可选内容裁剪由包布局信息记录，不自动提升应用所需基础环境。

新增可兼容字段不机械提升 `updateProtocolRevision`。确实改变事务语义且老 helper 不能理解时，才作为协议迁移处理，并要求同时提供过渡入口。

**Why:** 兼容依据对应实际运行要求，保留对未知环境的保护，也允许同一应用支持内容多寡不同的旧包。

**Alternatives considered:** 永久降低或跳过 runtime 校验会误接纳真实不兼容环境。仅给所有版本设置同一数字不能补齐依赖。只比较依赖文件差异也无法证明二进制能力兼容。

### 2. 纯 Python 应用依赖使用不可变的隔离集合

新增受版本管理的应用依赖锁清单。首个锁定包为 `websocket-client`，实现时选定经测试的精确版本及其 wheel SHA256，不沿用开放范围作为更新输入。每个包记录可信固定来源、摘要、Python 约束与允许的导入名称，传递依赖也必须完整锁定。

更新 helper 在安装级状态目录中准备按锁摘要寻址的依赖集合。依赖只从固定受信来源通过验证 TLS 下载，逐个校验摘要和 pure-Python wheel 兼容性。准备过程中不写入包内 `python/Lib/site-packages`，不使用无约束的 `pip install --upgrade`，不触发 sdist 构建或安装脚本。归档展开拒绝路径逃逸、链接和可执行启动钩子。

应用入口通过只读的标准库加载器，在导入业务模块前根据当前应用提交与清单选择已经完成校验的依赖集合。校验未完成的目录不会进入导入路径。禁止覆盖标准库、Torch/CUDA/NumPy 等基础模块，不使用系统 Python 或用户 `PYTHONPATH` 补缺。下载与安装只发生在显式升级或安装命令中，应用 import、status 和设置页打开时不执行。

新安装器与未来便携构建器消费同一份锁，不另写一套包版本。首次采用新机制的 Git 源码安装也有显式准备入口，避免依赖本机碰巧装过新模块。基础环境的已有依赖保持原样，应用锁中的包始终从匹配集合加载。

**Why:** 小依赖可以独立交付，不触碰多 GB 的基础环境。不可变目录让失败恢复和降级不必反向运行 pip，也避免依赖解析器升级核心计算库。

**Alternatives considered:** 直接修改全局 site-packages 会让 Git 回滚之后仍残留不兼容依赖。把库源码散落到业务目录会增加长期维护负担。要求系统 pip 或重新完整打包违背便携与小更新目标。原生扩展本轮不进入隔离集合。

### 3. 应用提交与依赖集合属于同一事务

沿用现有安装锁和 helper，在持久化事务中记录 previous/target SHA、各自的依赖锁摘要与集合标识。执行顺序为校验目标与基础兼容、准备依赖、停止旧服务、检出目标、验证匹配的代码与依赖、启动并探测新实例、确认完成。下载与准备失败发生在停止服务和修改应用之前。

依赖加载与应用提交绑定，不仅依赖可变的全局 active 指针。切换或中断后不会把新代码配上旧依赖。helper 检查目标导入、依赖版本、前端入口以及新实例 commit 后才能报告成功。回退时恢复 previous SHA 与其对应依赖选择，旧集合在成功确认前保留。

重启恢复根据日志与实际 HEAD 恢复一致组合。请求内对账继续只读且轻量，耗时校验与恢复由外部 helper 执行。升级到不使用隔离依赖的历史版本时停用新集合，清除新进程的继承导入路径，按旧版方式启动。集合清理只删除已证明不被当前事务、当前提交和恢复点引用的内容。

**Why:** 代码健康和依赖健康需要一起验收，才能保证失败之后仍能启动。下载尽量不影响当前使用。

**Alternatives considered:** 先升级代码再联网补依赖会制造无法启动的窗口。只恢复 Git、只保存一个 active 目录或在 import 时自动安装，都无法可靠处理断电与降级。

### 4. 为旧更新器交付持久可用的轻量过渡工具

正式发布流程生成小型 Windows 升级工具包及 SHA256，通过规范仓库的正式 Release 提供。用户把工具放入已有受管便携包后运行，工具使用包内 Python 与 MinGit。它只接受 Stable/Latest 以及检查模式，按规范仓库解析 exact SHA，不接受 URL、命令或任意 SHA 输入。

入口为标准库实现。它先以只读方式检查安装来源、基础环境候选基线、Git、dirty、活动任务和锁，再从规范仓库获取版本固定的可信迁移 helper，在与现有应用隔离的位置验证和运行。新的 helper 执行兼容与依赖联合事务，无需先覆盖旧更新器文件来绕开检查，也无需伪造包的 runtime 元数据。运行中的主应用只在依赖准备完成且写操作前全部条件复查通过后停止。

工具本身不要求目标应用已能导入新依赖。helper 版本与来源固定在发布产物中，跨后续发布保留下载入口和覆盖基线。维护中的工具针对新目标检查协议，不能处理时明确指向更新的轻量工具。无受管 Git 的旧包继续得到准确说明，不执行推断式修复。

**Why:** 旧代码无法理解新版规则，需要一次显式引导，但无需替换完整环境。永久入口不依赖用户赶上某个中间发布。

**Alternatives considered:** 只改新版 updater 到达不了旧客户端。短暂回退 main 或排列多个 Stable 桥接标签不能同时覆盖 4 和 6。要求手工编辑 JSON、改 runtime 数字或执行任意远程脚本无法形成可验证的升级流程。

### 5. 分类守卫与连续更新成为发布条件

兼容性 CI 区分应用依赖、基础环境和包布局。应用依赖变更必须带完整锁与准备/恢复验证，不能要求只提高 runtime 数字。基础环境改动必须更新真实兼容声明与迁移/新完整包要求。布局变动必须有裁剪证据，不隐含切断应用更新。未分类的敏感变化继续阻断。

新增错误码、依赖准备阶段与过渡工具指引同步到 API 类型、更新中心和中英文资源，复用已有 UI。常规状态查询不探测联网依赖，不在普通页面增加安装流程。

发布门槛至少包括旧包引导到修复版、修复版到后续依赖不同的版本 A、A 到版本 B、B 降回 Stable，以及每一步的自动失败恢复。版本号、构建产物和包来源必须可追溯，不把文件改名当成新环境交付。

**Why:** 保证后续可更新需要验证升级链，单次当前版本测试不足以证明这一点。

**Alternatives considered:** 仅对比版本号或只做合成环境测试会遗漏已发布包的实际启动形态；让每个小依赖继续触发完整包将重现本次问题。

## Risks / Trade-offs

- [旧包运行环境缺少未记录的基础能力] -> 从实际旧归档 clean-extract，记录出厂指纹与验证结果；仅将通过的 target/基线加入支持表。
- [依赖集合覆盖基础模块或导入恶意启动钩子] -> 固定可信 wheel 与哈希，限制归档和导入根，拒绝原生/脚本钩子及受保护模块，覆盖路径逃逸测试。
- [网络、磁盘或杀进程造成半成品] -> 完成标记与原子落盘，先准备再停服务，状态记录前后组合，逐阶段注入故障并恢复。
- [旧版入口加载了新版依赖] -> 按 checked-out commit 选择集合，重启移除继承路径，专门验证更新到旧 Stable 的行为。
- [基础环境之后真的不兼容] -> 明确告知所需新环境/完整包，保留原安装，不承诺任意历史环境永久运行全部新功能。
- [过渡工具后续不可得或协议再次演变] -> Release 保留持久入口与工具校验资料，每次更新协议变化要求工具覆盖证明，禁止依赖被最高版本标签越过的临时桥接版。
- [一份升级程序与常规 updater 长期分叉] -> 过渡入口仅做识别、获取和调用可信 helper，事务共用同一实现与测试。

## Migration Plan

1. 收集 runtime 4、6 的真实归档和校验资料，建立三 target 的验证目录与证据。若原始包暂不可得，不发布其兼容承诺。
2. 实现新清单、锁、只读依赖加载器与联合事务，保持现有包元数据和历史清单可读，不降低或伪造 runtime 数字。
3. 交付轻量过渡入口，通过实际旧包进入修复版；复测工作台真实 WebSocket 进度与核心功能启动。
4. 用两个测试版本覆盖依赖新增/升级/移除、重复更新、降级及恢复，更新 CI 与文档。
5. 在兼容分支合入 main 前完成源码与既有便携包回归。之后独立提升版本并发布应用与轻量升级工具，沿用经过验证的完整包链接。本轮不重建完整包。

回退由事务恢复旧应用和旧依赖选择，工作区、模型与基础运行环境逐项比较 hash。新机制发布前在临时目录执行，禁止用维护者现有运行目录作为故障注入目标。

## Open Questions

- 原始 runtime 4 三种归档是否都可从发布下载源取得并完成 SHA256 验证，需要在实现阶段确认。runtime 5 若曾单独分发，补充同等证据。
- `websocket-client` 的精确版本、可信 wheel 来源和 SHA256 在实现阶段锁定并测试，不在提案中填入未经验证的值。
- 三个 target 共享运行环境证据的部分可以复用，CUDA 与视频工具相关启动验证必须保留各自结果。
